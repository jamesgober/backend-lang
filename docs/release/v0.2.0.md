# backend-lang v0.2.0 — The Foundation of a Native Backend

**Machine IR, target descriptions, calling conventions, frames, parallel
moves, and emission, proven end to end.** v0.2.0 turns the scaffold into the
foundation of the LexerSketch native backend: a machine IR of target
instructions over virtual and physical registers, the backend half of the
target-description model (registers, classes, and instructions as data,
implicit operands included), SysV and Win64 calling conventions with frame
layout, a parallel-move resolver that is correct for every shape of copy, and
emission of physical-register functions to x86-64 machine code through
isa-lang. A function built by hand goes from MIR to isa-lang bytes to an
object-lang ELF executable to a running Linux process, whose exit status is
the program's answer.

## What is backend-lang?

The core of the `-lang` family's own native code generator, replacing rented
backends (Cranelift, LLVM) on the path from a language sketch to machine
code. It sits between the optimizer (pass-lang over ir-lang) and the encoder
(isa-lang): it owns machine IR, instruction selection, register allocation,
frames, and calling conventions. This release builds everything those passes
stand on; instruction selection and register allocation follow in 0.5.

## What's new in 0.2.0

### Machine IR

A `Function` is blocks of target instructions. Instructions name virtual
registers (typed by a register class), physical registers, stack slots, and
other functions by symbol; each instruction may carry extra implicit uses,
definitions, and clobbers (a call's argument and result registers and its
convention's clobbers). Operands are checked against the instruction's
description as they are added, `verify` checks block structure and SSA
single definition in linear time, and the text form is deterministic:

```text
function sum (sysv64) {
block0(%0:gpr):
    %4:gpr = mov64ri 0
    jmp block1(%4, %0)
block1(%1:gpr, %2:gpr):
    %5:gpr = add64 %1, %2
    %6:gpr = sub64 %2, 1
    jcc ne, block1(%5, %6), block2(%5)
block2(%3:gpr):
    rax = copy %3
    ret implicit(rax)
}
```

Values cross edges as **block parameters**: the same information as phi
nodes, kept on the edge as the parallel copy it implies. ir-lang already
uses block parameters, and an SSA register allocator resolves each edge with
the same resolver the emitter uses.

### Target descriptions, as data

A `Target` lists registers, classes (with allocatable sets and spill sizes),
and instructions. Each instruction row gives its operand rules (definitions,
uses with accepted shapes and immediate ranges, two-address ties, condition
codes, branch targets) and the registers it touches without naming them:
`idiv64` reads and writes `rdx:rax`, a shift by `cl` reads `rcx`, `syscall`
clobbers `rcx` and `r11`. The flags are a physical register; an instruction
that might leave some flags unchanged also reads them, so no flag value ever
appears to come from an instruction that might not have produced it. The
x86-64 table has 91 rows, each mapped to the isa-lang instruction it encodes
as; a test emits every row over 913 operand shapes and checks its flag
effects and fixed registers against isa-lang's own description.

### SysV and Win64, and frames

`SYSV` and `WIN64` describe argument and return registers (separate counters
or by position), callee-saved sets (Win64's `xmm6`-`xmm15` included), call
clobbers, stack alignment, shadow space, red zone, and the stack-probe
interval. `layout_frame` saves the callee-saved registers a function writes,
places locals by alignment above the outgoing area, keeps the stack 16-aligned
at calls, uses the SysV red zone for small leaves, and probes frames of a page
or more one page at a time:

```rust
use backend_lang::mir::{Function, SlotKind};
use backend_lang::target::frame::FrameStep;
use backend_lang::x86_64::WIN64;

let mut f = Function::new("big", &WIN64);
let _buffer = f.stack_slot(SlotKind::Local { size: 10_000, align: 16 })?;
let frame = f.frame_layout()?;
assert!(matches!(frame.prologue().last(), Some(FrameStep::Alloc { probe: 4096, .. })));
# Ok::<(), Box<dyn std::error::Error>>(())
```

### The parallel-move resolver

Every control-flow edge with arguments, every `copy` and `pcopy`, and later
every register-allocation fix-up and call setup is a parallel copy. The
resolver handles any of them: permutations, cycles of every length, fan-out,
registers and stack slots mixed, and immediates. Trees drain leaves first; a
cycle is broken for free when one of its values was already copied out of it,
by `k - 1` swaps when it is all registers (x86-64 `xchg`), or through a
scratch location otherwise. Memory-to-memory moves go through a free
register, or a register borrowed around the move and restored. This is the
fix for the class of bug codegen-lang shipped (ISSUES H01): a back edge that
swaps its parameters.

```rust
use backend_lang::moves::{self, Move, MoveEnv, Step};
use backend_lang::x86_64::{self, GPR, RAX, RBX};

let swap = [Move::new(RAX, RBX, GPR), Move::new(RBX, RAX, GPR)];
let steps = moves::resolve(&x86_64::TARGET, &swap, &MoveEnv::new())?;
assert_eq!(steps, [Step::Swap { a: RAX, b: RBX, class: GPR }]);
# Ok::<(), backend_lang::moves::MoveError>(())
```

### Emission

`emit` (one function) and `Emitter` (several, calling each other by name)
take physical-register functions to machine code through isa-lang's
assembler: the prologue and epilogues from the frame plan, every
instruction through its row's isa-lang mapping, every edge's parallel copy
resolved (a conditional branch whose taken edge carries moves branches
around them, so critical edges need no extra block), calls patched and
branches relaxed by isa-lang. Virtual registers, mismatched tied operands,
and writes to the stack or frame pointer are reported, not emitted.

## Tests and verification

- **An interpreter as oracle.** The test suite carries a small x86-64
  interpreter written against isa-lang's decoder; it runs emitted code on
  every platform and checks stack alignment at every call.
- **Parallel copies.** Resolver property tests against a parallel-assignment
  reference (random copies built from explicit cycles, chains, fan-out, and
  immediates; every step checked executable on x86-64; every untouched
  location checked unchanged); exact minimal step counts for register-only
  copies; cycles of every length to 14 registers and 64 slots; a
  100,000-slot permutation. Emitted jump and branch edges over all fourteen
  allocatable registers and up to six slots are executed and checked
  location by location, in all four branch shapes. A deliberately broken
  swap fails four of these tests.
- **The table.** Every opcode over 913 operand shapes emits and decodes back
  to its mnemonic, with flag effects and fixed registers matching isa-lang.
- **Frames.** Property tests simulate random prologues under both conventions:
  alignment at calls, slot alignment and disjointness, clearance from saved
  registers and the outgoing area, exactly the right registers saved.
- **End to end.** A Fibonacci loop with parallel-copy edges and a stack-slot
  parameter (exit 55), recursive factorial across two functions (exit 120),
  and a mix of the table with an indirect call through a function address
  (exit 200) are wrapped by object-lang 0.2 into static ELF executables; on
  Linux x86-64 they run as processes and their exit status is checked, and
  everywhere they run in the interpreter.
- **Hostile construction.** Random opcodes with valid, foreign, and
  ill-shaped operands never panic the builder, verifier, printer, frame
  layout, or emitter.
- A deep run of the property tests at 100,000 resolver cases, 40,000 emitted
  edges, and 100,000 frame and hostile-construction cases found nothing.

## Dependency wiring

`isa-lang` 0.2 is wired: every byte of the encoding is isa-lang's.
`object-lang` 0.2 is a dev-dependency for the end-to-end test only: turning
code into an executable is the AOT driver's job. `ir-lang` is not wired:
instruction selection needs ir-lang 2.0 (calls, memory, aggregates) and comes
in 0.5. `pager-lang` is not wired: making code executable is the JIT's job.
The decisions, and every item moved to 0.5 with its reason, are recorded in
`dev/ROADMAP.md`.

## Breaking changes

**None.** v0.1.0 had no public API.

## Verification

Run on Windows x86_64 on Rust stable and on the 1.85 MSRV:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo test --no-default-features
cargo +1.85 test --all-features
cargo bench --no-run
```

All green. Counts at this tag, identical with all and with no default
features: 17 unit tests; 39 integration tests (8 of them property tests); 274
doctests (including every `rust` example in `README.md` and `docs/API.md`).
On Windows the executable test checks the files and runs the programs in the
interpreter; the native run is compiled for Linux x86-64 only and is part of
the Linux gate.

Benchmarks (`cargo bench --bench bench`, release profile, Windows x86_64,
library-only):

| Benchmark | Time |
|---|---:|
| Build a 100,000-instruction function | ~4.3 ms |
| Verify it | ~1.3 ms |
| Emit it (verify, frame, every edge, encode, relax) | ~10.5 ms |
| Resolve a 4-register permutation | ~150 ns |
| Resolve a 100,000-location permutation | ~11 ms |
| Resolve 100,000 four-move edges, one resolver | ~17 ms |
