# backend-lang v0.4.0 — OPS v2 and an Allocator That Does Not Start Over

**ir-lang 2.0.0-alpha.3, integer and float `pow`, saturating shifts, and
register allocation that updates its liveness instead of recomputing it.**
v0.4.0 moves the backend to the ir-lang version irgen-lang and opt-lang
target (ISSUES P37), so the native path from HIR to machine code has one
IR version end to end; selects all of OPS v2 and checks it against ir-lang's
interpreter on the processor; tests the SSA ir-lang's variables API and
`insert_statepoints` produce exactly as they produce it; and takes compile
throughput on the 100,000-instruction benchmark above 1M IR instructions per
second (ISSUES P32).

## What is backend-lang?

The `-lang` family's own native code generator, replacing rented backends
(Cranelift, LLVM) on the path from a language sketch to machine code: ir-lang
2.0 in, through instruction selection, SSA register allocation with exact
stack maps, and emission through isa-lang, x86-64 code with symbols,
call-site records, data, and relocations out. jit-lang 2.0 and aot-lang 2.0
are its consumers.

## What's new in 0.4.0

### ir-lang 2.0.0-alpha.3

```toml
backend-lang = "0.4"   # re-exports ir-lang =2.0.0-alpha.3 as backend_lang::ir_lang
```

Selection follows ir-lang's fallibility rule, `BinaryOp::can_error(policy,
ty)`: a signed `pow` and a signed saturating shift can fail under every
policy, so they arrive only as the operation of a `check`, and whatever they
raise goes to its error edge. Under `overflow = trap`, an unrepresentable
power still traps with code 1, but a negative exponent is the
`NegativeExponent` error, code 6, on the edge (ISSUES P36, fixed in
alpha.3).

### OPS v2

```rust
use backend_lang::Options;
use ir_lang::{BinaryOp, BlockArg, BlockCall, InstData, Linkage, Module, Overflow, Policy, Signature, Type};

// ipow(x, e) = x ** e, or the error code when it fails.
let mut m = Module::new("demo");
let f = m.declare_function("ipow", &Signature::new(&[Type::I64, Type::I64], &[Type::I64]), Linkage::Export)?;
let mut b = m.build(f)?;
let (x, e) = (b.param(0)?, b.param(1)?);
let ok = b.create_block(&[Type::I64])?;
let err = b.create_block(&[Type::U32])?;
let pow = InstData::Binary { op: BinaryOp::Pow, policy: Policy::overflow(Overflow::Error), args: [x, e] };
b.check(pow, BlockCall::with_args(ok, &[BlockArg::Result(0)]), BlockCall::with_args(err, &[BlockArg::ErrorCode]))?;
b.switch_to(ok)?;
let r = b.block_param(ok, 0)?;
b.ret(&[r])?;
b.switch_to(err)?;
let code = b.block_param(err, 0)?;
let code = b.convert(ir_lang::ConvOp::Zext, Policy::NONE, code, Type::I64)?;
b.ret(&[code])?;
let c = backend_lang::compile(&m, &Options::sysv())?;
assert!(c.imports().is_empty()); // integer pow needs no runtime
# Ok::<(), Box<dyn std::error::Error>>(())
```

- **Integer `pow`**: repeated squaring, a square taken only while a higher
  exponent bit remains, so every product computed is a factor of the result
  and overflow can be checked after each. A constant exponent unrolls (at
  most 64 squarings and 64 multiplications); a run-time one is a four-block
  loop over its bits (at most 64 iterations). `wrap` multiplies at 64 bits;
  `trap` and `error` check `imul`'s overflow, `mul`'s for `u64`, and compute
  8/16/32-bit types exactly in 64 bits with a range check at the end.
- **Saturating shifts**: an amount at or past the width shifts every bit
  out (zero, or the sign for an arithmetic right shift); a negative signed
  amount is still `ShiftOutOfRange` on the error edge. Constant amounts fold;
  run-time ones use a `cmov` or clamp the count.
- **Float `pow`**: a call to the runtime's routine,
  `Options::pow_f64_symbol` / `pow_f32_symbol` (defaults
  `__lexersketch_pow_f64`, `__lexersketch_pow_f32`), under the C convention
  with the bit patterns in integer registers. The routine must be ir-lang's
  `ls_pow` (for `f32`: widened, computed, rounded once), so the result is the
  same bits on every tier. **Why a call and not compiled code:** `ls_pow` is
  IEEE double arithmetic throughout (double-double `log` and `exp`); isa-lang
  0.2 encodes no SSE, so compiling it now would mean emulating every one of
  its `+ - * /` in integer code, thousands of instructions per `pow`, to be
  replaced when SSE arrives. A call to `ls_pow` itself is bit-identical by
  construction, and the tests bind exactly that.
- **Floats as bit patterns**: so a float can reach `pow` and come back,
  constants, `bitcast` to and from the integer of the same width, loads,
  stores, `select`, and block parameters and edge arguments carry float bits
  in general-purpose registers. Other float operations, and float arguments
  and results, are still refused (ISSUES P11).

### Allocation without starting over

0.3's allocator reran liveness and coloring on every spill round. 0.4 builds
a use index once (in a walk that also checks dominance), analyses liveness
once, and collects affinities once; each spill round reports what it
changed, and the analysis is updated in place. The update is exact because
spill code reads and writes no physical register, every spilled value
leaves every live-in set, and each reload temporary lives only from just
before its user to the user. Spill rewriting visits only the spilled values'
uses, only blocks that received spill code are rebuilt, and the final
substitution rewrites operands in place. A round now costs one coloring
walk.

## Tests and verification

- **OPS v2 conformance**: `pow` under `wrap`, `trap`, and `error` and
  saturating `shl`/`shr` on every integer type over the OPS edge values,
  with run-time operands and with every edge value as a constant, in the
  test interpreter under SysV and Win64 and natively, against ir-lang's
  interpreter.
- **Float `pow`**: `f64` and `f32` over signed zeros, infinities, NaNs and
  NaN payloads, subnormals, odd and even integers, and random magnitudes,
  with run-time and constant exponents, compared bit for bit with `ls_pow`,
  in the test interpreter and natively (a mutation that swaps the operands
  is caught).
- **Random programs**: the generator now emits `pow` and saturating shifts
  (plain where they cannot fail, `check`ed where they can) and float `pow`
  through constants, `select`, memory, and joins. A deep run at 3,000
  programs per sweep (differential, native, variables) passed.
- **Variables API**: random programs built only with `declare_var`,
  `def_var`, `use_var`, and `seal_block` (unsealed loop headers, joins,
  unassigned reads, `check`ed OPS v2 whose error edges assign variables,
  calls), against the interpreter in the test interpreter and natively.
- **Statepoints from ir-lang**: GC programs whose lists
  `insert_statepoints` added, under the moving collector that walks real
  frames by the call-site records (and natively with a non-moving one);
  `invoke`s whose relocated references `insert_statepoints` passes as
  results on both edges, through the minimal unwinder.
- **Dead error edges**: `check`s whose error successor is a shared block
  ending in `unreachable` (the shape opt-lang 0.3 produces) select to `ud2`
  and run against the interpreter, in the test interpreter and natively.
- **Hostile and huge inputs**: any OPS v2 operation with any constant or
  run-time operands compiles, terminates, and agrees (property test); the
  largest constant exponents unroll to bounded code; a 300,000-instruction
  function, 20,000 nested branches, a 2,000-parameter join, and 10,000 `pow`
  loops compile; the live budget is exact to the entry and unaffected by
  spill rounds; hostile MIR is rejected with exactly `verify_ssa`'s error.
- The allocator's independent point-by-point checker now also covers
  functions with `pow` loops and float bit patterns (the generator's).

## Dependency wiring

- `ir-lang` `=2.0.0-alpha.3` (was `=2.0.0-alpha.1`), re-exported; its
  `interp` feature is the dev-dependency oracle.
- `isa-lang` 0.2 unchanged; `object-lang` 0.2 stays a dev-dependency.
- **irgen-lang 0.2.0 is not a dev-dependency and cannot be**: it pins
  `ir-lang = "=2.0.0-alpha.2"`, and cargo resolves one version per
  compatible range (both are `2.0.0` pre-releases), so the two pins
  conflict. The HIR → ir → machine code end-to-end test belongs to
  irgen-lang 0.3 on alpha.3 (ISSUES P37); here the variables API and
  `insert_statepoints`, which irgen uses to build its output, are tested
  directly. Recorded in `dev/ROADMAP.md`.

## Breaking changes

- The ir-lang pin (`=2.0.0-alpha.3`), with alpha.2's and alpha.3's rules
  (signed `pow` and signed saturating shifts only inside `check`).
- Float constants, `bitcast`s, loads, stores, `select`, and edges compile
  instead of being refused; a module using float `pow` imports the runtime's
  `pow` routine.
- `Allocation::max_pressure` is the pressure before any spilling (0.3: the
  final round's).

`Options` gained `pow_f64_symbol`, `pow_f32_symbol`, and
`with_pow_runtime`; it is `#[non_exhaustive]`, so this is additive. The
migration table is in the CHANGELOG.

## Known limitations

Recorded with reasons in `dev/ROADMAP.md`:

- **Float arithmetic** other than `pow`, float comparisons and conversions,
  float arguments and results: isa-lang SSE (ISSUES P11). Float `pow`
  depends on the runtime providing `ls_pow` under the documented names.
- **The high-pressure benchmark stays below 1M IR instructions/s** (numbers
  below): no live-range splitting (v0.5.0).
- No unwind tables, no PIC/GOT, no `lock`-prefixed atomics, no AArch64, no
  aggregates by value (all v0.5.0, unchanged from 0.3).

## Verification

Run on Windows x86_64 on Rust stable, 1.99, and the 1.85 MSRV:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo +1.99 clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo test --no-default-features
cargo +1.85 test --all-features
cargo bench --no-run
```

All green. Counts, identical with all and with no default features and on
1.85: 19 unit tests; 92 integration tests across 15 files (15 new: OPS v2
and float `pow` conformance, the variables API, inserted statepoints, dead
error edges into `unreachable`, hostile and huge inputs), plus 5 ignored
(statistics, timing, a one-seed debugging aid); 335 doctests, including
every `rust` example in `README.md` and `docs/API.md`. On Windows the native
sweeps run in-process; the Linux process runs (`executable.rs`, `link.rs`)
are part of the Linux gate.

Performance, Windows x86_64, release profile, library-only. **Measured while
other builds shared the machine**, so 0.4 and 0.3 were run alternately in
the same session (the ignored timing tests in `tests/differential.rs`, ten
runs each, three compiles per run) and are reported as median and best:

| Measurement | 0.3 | 0.4 |
|---|---:|---:|
| `compile`, 100,000-instruction function, median | ~104.5 ms (~0.96 M IR instructions/s) | ~76.2 ms (~1.31 M/s) |
| The same, best run | ~85.7 ms (~1.17 M/s) | ~65.9 ms (~1.52 M/s) |
| Register allocation alone, median / best | ~70.7 / ~56.3 ms | ~45.1 / ~35.8 ms |
| High-pressure function (45,833 IR instructions), select + allocate + emit, median / best | ~184.5 / ~154.7 ms | ~129.8 / ~103.1 ms (~0.44 M/s best) |

The target (≥1M IR instructions/s on `compile_100k`) is met by the median
and by 23 of 30 compiles in the session (0.3: 11 of 30); the slowest runs,
under the heaviest load, took up to ~147 ms (0.3: ~242 ms). In a quiet
moment 0.3 also crossed 1M/s at its best, which is why 0.3's notes called
the target "not demonstrated" rather than missed. Selection and emission are
unchanged (~14.7 and ~19 ms median); allocation went from about two thirds
of the pipeline's median time to about three fifths.
